## 1. 기획 의도와 독자

모델이 응답하는 데 성공하는 것과 사용자의 업무를 처리하는 데 성공하는 것은 서로 다른 검증을 요구한다. 이 책은 그 사이에 필요한 데이터 처리, 검색, 실행 제어, 평가, 운영을 하나의 서비스로 연결한다. 각 장은 작은 구현에서 시작해 실패를 관찰하고, 그 실패를 해결하는 설계의 비용까지 설명한다. 도구 사용법을 배운 독자가 제품 요구사항에 맞춰 기술을 선택할 수 있게 하는 것이 집필 목적이다.

독자는 Python 코드를 읽고 수정하며 HTTP 요청과 데이터베이스의 기본 동작을 이해하는 개발자다. 머신러닝과 선형대수는 선수 과목으로 두지 않는다. 벡터와 확률 등은 등장하는 시점에 필요한 직관, 기호, 계산 예를 설명한다. Python 환경 구성과 비동기 호출의 기초는 부록에서 보충한다.

로드맵의 역할 정의는 사전 학습 모델의 실용적 활용에 중심을 둔다. 이에 맞춰 학습 알고리즘이나 대규모 사전 학습은 범위 밖에 두고, 학습과 추론의 차이는 설명한다. [기준 로드맵](https://roadmap.sh/ai-engineer)

예상 규모는 6부 18장과 부록이다. 본문은 공백 포함 약 24만~32만 자를 편집상의 초기 예상으로 삼고, 장의 목표를 충분히 달성하는지에 따라 조정한다. RAG와 도구 실행에는 여러 단계의 실습을 배정하고, 기술 동향과 개발 도구는 상대적으로 짧게 다룬다. 분량 자체를 완료 기준으로 사용하지 않는다.

## 2. 기준 자료와 재구성

2026-09-08에 공식 웹페이지 HTML의 내장 데이터를 해석해 도표 객체를 확보했다. 객체의 갱신 시각은 2026-08-17이며 화면 구성 요소 279개와 명시적 연결 41개를 확인했다. PDF와 현재 웹 데이터에는 차이가 있으므로 현재 웹 데이터를 목차의 기준으로 삼는다. 추출 방법과 검증 결과는 `ROADMAP-VERIFICATION.md`에 기록한다. [현재 로드맵](https://roadmap.sh/ai-engineer)

연결의 방향은 필수 학습 순서를 뜻한다고 단정하지 않는다. 일부 연결은 제목이나 영역 라벨을 향하며, 직선 자체가 별도 화면 요소이기도 하다. 책은 확인된 영역과 연결을 참고하되 독립적인 선수 지식 순서를 설계한다.

책의 순서는 저자의 교육 설계다. 먼저 요청과 응답의 계약을 만들고, 지식을 공급하고, 업무를 실행하고, 이를 평가·운영하는 흐름으로 재배치한다. 안전성은 15장에서 종합하되 첫 API 호출부터 비밀 관리, 검색부터 접근 통제, 도구 호출부터 실행 권한을 적용한다. 평가는 16장에서 체계화하지만 작은 평가 질문 집합은 1장부터 유지한다.

## 4. 프로젝트의 단계별 발전

가상 조직의 업무 안내 문서로 질문에 답하고, 필요한 경우 지원 티켓을 조회·등록하는 서비스를 만든다. 데이터와 사용자 계정은 교육용으로 제작한다. 문서에는 식별자, 개정 시점, 부서별 접근 권한을 부여한다. 최신 개정과 이전 개정이 충돌하거나, 답이 없는 질문과 악의적인 문서가 들어오는 경우도 포함한다.

| 단계 | 해당 장 | 새 기능 | 통과 증거 |
|---|---|---|---|
| 요구 정의 | 1–2 | 시나리오와 모델 선택 | 초기 질문·실패 분류·판단표 |
| 최소 호출 | 3 | CLI와 제공자 경계 | 성공·시간 초과·오류 응답 실행 |
| 출력 계약 | 4–5 | 예산과 데이터 검증 | 초과 입력·잘못된 출력 처리 |
| 실행 대안 | 6 | 로컬 모델 | 실행 환경과 비교 결과 |
| 문서 검색 | 7–8 | 색인과 권한 필터 | 검색·갱신·삭제·접근 통제 테스트 |

빠른 학습 경로는 필수 내용만 순서대로 따른다. 심화 실습 없이도 문서 질의와 도구 실행, 평가와 로컬 배포까지 완성할 수 있게 구성한다. 학습, 영상, 이미지 생성은 주 프로젝트의 실행을 막지 않는 별도 실습으로 둔다.

## 5. 집필·검증·퇴고 기준

전문적인 ‘~다’체를 사용한다. 첫 등장 때 필요한 용어만 영어를 병기하고, 이후 용어를 통일한다. 개념 설명은 문제, 원리, 최소 구현, 실패 조건, 측정 방법, 대안 선택의 질문에 답해야 한다. 모든 절에 같은 소제목을 반복하지는 않는다.

장 초안은 관련 공식 문서 검증 → 절별 본문 → 구현과 실패 재현 → 기술 검토 → 문장 퇴고 순서로 작성한다. 장마다 학습 목표와 결과물의 연결을 확인하고 중복 설명은 앞 장 참조로 정리한다. 그림은 데이터 흐름과 권한 경계를 설명하는 데 사용하며 장식용으로 추가하지 않는다.

모든 수치는 실측·출처 인용·교육용 가정으로 구분한다. 코드의 문법 확인, 모의 테스트, 실제 모델 통합 실행을 서로 다른 증거로 기록한다. 실행하지 않은 코드를 검증 완료로 표시하지 않는다. 모델·패키지의 정확한 버전은 실행 환경을 구성한 뒤 기록하며 지금 추정해 고정하지 않는다.

최종 완료에는 전체 장 본문, 예제와 설명의 일치, 학습 목표별 검증 기록, 주요 주장 출처, 편집 메모 정리, 용어·문체 퇴고, 사이트 빌드 및 책의 이동·목차·검색·사이트맵 검증이 필요하다. 목차 파일이나 빈 장 파일만으로 완료를 판정하지 않는다.

## 6. 저장 위치와 현재 상태

기획·검증 기록은 저장소의 `books/ai-engineering/`에 둔다. 본문은 기존 사이트 구조인 `src/content/book/ai-engineering/`에 두어 `/books/ai-engineering/` 아래에 출력한다. 본문을 시작할 때 책 메타데이터와 부별 장 파일을 추가한다.

기획 제안과 현재 로드맵 대조를 마친 뒤 v2를 집필 기준으로 확정했다. 첨부 지침에는 별도의 사용자 승인 요구가 없으며 완성본 제작이 이미 요청되어 있으므로 순차 집필을 진행한다. 이는 사용자가 목차를 승인했다고 기록하는 것이 아니라, 승인 단계를 임의로 추가했던 앞선 해석을 정정한 것이다. 최종 목표인 완성본 제작은 계속 유지한다.
