다음 분기 첫날이면 개발팀은 전 직원에게 링크를 다시 보내야 했다. 그동안 고쳐 온 봇을 그때까지 써 본 사람은 총무팀 담당자 한 명뿐이었고, 개발팀도 한 군데 고칠 때마다 각자 노트북에서 한 번씩 불러 보는 것으로 그쳤다. 두 사람이 동시에 물어본 적조차 없었다.

같은 모델과 프롬프트라도 혼자 부를 때와 여러 사용자가 기다릴 때는 다르게 움직인다. 요청이 줄을 서고, 연결이 끊기고, 문서와 프롬프트의 버전이 바뀐다. 운영은 모델을 서버 프로세스에 넣는 일로 끝나지 않는다. 요청을 받아도 되는지 판단하고, 실패 위치를 찾고, 이전 상태로 돌아갈 수 있어야 한다. 개발팀은 공개 날짜 전에 이 봇을 서버에 올려 두 사람이 동시에 물어보게 해 보고, 줄이 밀리고 마감을 넘기는 상황은 실제 모델 대신 가짜 대기 시간을 넣어 따로 돌려 보기로 했다.

## 요청 경로와 배포 단위

<ServeRequestPath />

```bash
books/ai-engineering/examples/.venv/bin/python books/ai-engineering/examples/book_service.py --state /tmp/hanul-book init
export BOOK_LOCAL_TOKEN="$(python3 -c 'import secrets; print(secrets.token_urlsafe(32))')"
books/ai-engineering/examples/.venv/bin/python books/ai-engineering/examples/book_service.py --state /tmp/hanul-book serve --port 8765 --prompt-version rag-local-v2
```

`book_service.py`는 SQLite 저장소, `respond`, 로컬 E5와 Qwen을 연결한다. `init`은 가상 교육비 개정 문서와 `hanul/reader`의 권한을 준비한다. 다시 돌려도 순번과 지문이 같으면 문서 저장소가 `unchanged`로 넘긴다. `init`이 한 번 준비할 뿐, 서비스가 뜰 때마다 권한을 새로 주지는 않는다. 토큰은 현재 터미널의 환경에만 두고 커밋이나 로그에 남기지 않는다. `ready`가 찍히면 모델이 다 올라오고 포트가 열렸다는 뜻인데, 거기까지다. 답이 제대로 나오는지는 이 한 줄로 알 수 없다. Python 공식 문서도 `http.server`를 운영용으로 권하지 않는다. [Python HTTP 서버 문서](https://docs.python.org/3/library/http.server.html)

```python
import json, os, urllib.request
request = urllib.request.Request(
    "http://127.0.0.1:8765/ask",
    data=json.dumps({"question": "교육비 한도와 신청 순서는?"}).encode(),
    headers={"Content-Type": "application/json",
             "Authorization": "Bearer " + os.environ["BOOK_LOCAL_TOKEN"]},
)
with urllib.request.urlopen(request, timeout=60) as response:
    result = json.load(response)
```

클라이언트가 받은 HTTP 200 안에도 `contract_failed`가 있을 수 있다. 요청 처리와 업무 결과를 나눠 응답 본문에 업무 상태를 싣는다. 제품 API라면 상태별 HTTP 매핑을 명세로 정해 모든 클라이언트가 같은 뜻으로 읽게 한다.

## 추적 ID와 관측 신호

추적 ID는 한 요청이 지나간 경로를 하나로 묶는 식별자다. 프로세스가 여럿이면 요청 하나의 추적을 검색과 모델 호출, 도구 실행 구간으로 다시 쪼갠다. OpenTelemetry는 이 구간을 span이라 부르고 부모·자식 관계와 속성·이벤트를 붙인다. `book_service.py`는 요청마다 새 ID를 만들고 상태, 프롬프트 버전, 전체 처리 시간을 JSON 로그로 남긴다. 질문·문서·토큰은 기본 로그에 없다. 다른 시스템과 연결할 때 바깥에서 들어온 추적 헤더를 업무 권한으로 쓰지 않는다. [OpenTelemetry 추적 개념](https://opentelemetry.io/docs/concepts/signals/traces/)

| 신호 | 항목 |
|---|---|
| 기본 네 축 (Google SRE) | 지연 · 요청량 · 오류 · 자원 포화 |
| AI 품질 신호 | 생성 완료율 · 형식 실패 · 근거 부족 · 인용 실패 · 확인 대기 |
| 근거 부족이 늘었을 때 함께 볼 것 | 검색 후보 수 · 색인 버전 · 권한 변경 · 생성 호출 유무 |
| 라벨로 쓰지 않을 것 | 오류 문자열 전문 · 사용자 ID · 질문 |

근거 부족이 늘었다고 바로 장애가 아니다. 답할 수 없는 질문이 늘었을 수도, 권한·색인·문맥 구성이 잘못됐을 수도 있다. 상태 코드는 몇 가지로만 정해 두고, 요청마다 다른 세부는 권한을 건 로그나 추적에서 찾아본다. [Google SRE 모니터링](https://sre.google/sre-book/monitoring-distributed-systems/)

## 큐 · 백프레셔 · 마감

<QueueDeadline />

```python
try:
    async with asyncio.timeout_at(deadline):
        await simulated_dependency()
except TimeoutError:
    status = "deadline_exceeded"
```

요청을 동시에 돌리면 처리량이 늘 수도 있지만, 그만큼 요청끼리 모델 메모리와 CPU·GPU를 두고 다툰다. 같은 모델을 워커마다 복제하면 가중치 메모리도 는다. 대기열은 순간 유입을 흡수하지만 무제한이면 대기 시간과 메모리를 쌓는다. 줄의 길이가 그대로 기다리는 시간이다. 워커가 초당 두 건을 처리하는데 앞에 스무 건이 서 있으면 지금 접수한 요청은 10초를 기다려야 차례가 온다. 유입이 처리 속도보다 빠른 동안에는 줄이 계속 길어지고 대기 시간도 함께 길어진다. 그래서 큐에 상한을 두고 넘치면 접수 단계에서 거부한다. 거부도 실패지만, 끝까지 기다렸다가 마감을 넘긴 요청은 자원을 다 쓰고 나서 실패한다. 개발팀이 `operations_demo.py`로 부하를 걸어 보니 큐에 자리가 있던 넷만 들어가고 나머지 16건은 접수 단계에서 바로 거부됐다. 다만 이 숫자는 실험이 요청을 한꺼번에 몰아 주고 워커를 둘만 둔 결과다. 요청이 끊이지 않고 들어올 때 얼마나 받아 낼 수 있는지는 따로 재야 한다.

다만 마감을 걸어 둔다고 모든 작업이 그 자리에서 멈추지는 않는다. `asyncio.timeout_at`의 취소는 협력적인 비동기 작업에서 작동한다. 동기 CPU 추론이나 이미 시작한 외부 쓰기는 되돌리지 못한다. `to_thread`로 옮긴 작업은 태스크를 취소해도 스레드 안에서 돌던 연산이 그대로 이어진다. 실제 모델 서비스에는 추론 엔진의 취소 기능, 워커 격리, 종료·정산 절차가 필요하다. `book_service.py`는 요청을 순서대로 처리하고 본문 길이 상한과 소켓 타임아웃만 둔다. 추론을 강제로 끊는 마감과 비동기 큐는 아직 넣지 않았다. [Python 비동기 큐](https://docs.python.org/3/library/asyncio-queue.html), [Python 태스크와 취소](https://docs.python.org/3/library/asyncio-task.html)

## 지연 분포와 캐시

평균 응답 시간이 같아도 일부 사용자는 훨씬 오래 기다린다. p50·p95 같은 분위수와 시간 초과 비율을 함께 적고 거부한 요청과 성공한 요청의 분포를 나눈다. 빠르게 거부한 요청을 섞으면 지연이 실제보다 짧아 보인다. 개발팀이 그 부하 실험에서 p95를 낸 표본도 받아들인 네 건뿐이었다. 표본이 넷이면 p95가 가장 느린 요청과 거의 같아져서, 이 값 하나로 지연을 말하기에는 이르다. 실제 부하 실험에는 워밍업, 동시성, 도착률, 입력·출력 길이 분포, 실행 시간, 실패와 재시도가 들어간다. 토큰을 얼마나 썼는지 모르면 비용도 모르는 채로 둔다. 로컬 모델도 장치를 돌린 시간과 놀린 시간, 저장 공간, 운영과 검토에 들인 손을 모두 비용으로 친다.

응답 캐시 키에는 질문만이 아니라 조직·권한 범위, 문서 개정, 프롬프트·모델·스키마, 기준일이 들어가야 한다. 권한을 거둬들인 뒤에도 캐시에 있던 답을 그대로 주면 검색 단계의 권한 검사를 거치지 않은 답이 나간다. 의미 캐시는 “출장비”와 “해외 출장 숙박비”처럼 비슷하지만 정답 조건이 다른 질문을 합칠 수 있다. 개발팀은 최종 답변 캐시를 아직 두지 않았다. 나중에 넣는다면 정확 일치 기준선과 무효화 테스트를 먼저 만든다.

## 장애 주입과 복구

```bash
books/ai-engineering/examples/.venv/bin/python books/ai-engineering/examples/operations_demo.py
```

<FaultRuns />

개발팀은 의존성 하나가 0.01초 대신 0.2초를 쓰게 해 놓고 같은 부하를 다시 걸었다. 받아들인 네 건이 전부 접수 기준 마감인 0.05초를 넘겼는데, 이전 버전으로 되돌리자 네 건이 다시 끝까지 갔다. 실제 복구 절차에는 감지, 영향 범위 확인, 신규 요청 제한, 실행 중 작업 처리, 이전 버전 전환, 정상·실패 사례 재확인이 들어간다. 티켓이 등록됐는지 알 수 없을 때는 같은 멱등성 키로 상태를 다시 조회하거나 그 키 그대로 한 번 더 보낸다. 새 키로 다시 등록해 복구하면 중복 업무가 생긴다. 프로세스를 내릴 때도 접수 중단과 실행 중 요청 처리를 나눈다. 읽기 요청은 취소하면 되지만 이미 외부 시스템에 넘긴 변경은 결과를 확인해야 한다. 로컬 티켓은 같은 파일 DB에 있어서 CLI 프로세스가 바뀌어도 같은 초안을 다시 실행해 보고 결과가 같은지 확인할 수 있다.

## 관측 도구와 범위

관측 도구를 고를 때는 추적 조회, 지표 집계, 경보, 평가 결과 연결, 운영 편의성을 본다. 전송할 데이터의 범위·저장 위치·보관 기간·권한·내보내기도 함께 본다. 화면이 보기 좋다는 이유로 원문 질문과 문서 전체를 기본값으로 내보내지 않는다. 개발팀이 이 서버에서 확인한 것은 로컬 HTTP 기능 연결, 허용 필드 로그, 파일 DB의 티켓 재실행, 합성 부하의 백프레셔·마감·복귀까지다. 인터넷 배포와 다중 사용자 인증, 실제 모델에 동시 부하를 거는 일, 외부 티켓 시스템이 끊겼을 때의 복구는 아직 손대지 못했다. 서버가 돌아가도 모델 품질에 걸어 둔 채택 보류는 풀리지 않는다.

개발팀이 각자 노트북에서 한 번씩 불러 보던 봇을 이제 서버 하나가 받는다. 두 사람이 동시에 물어도 어느 요청이 줄에서 밀렸는지 추적 ID로 따라간다. 다음 분기 첫날까지 개발팀이 붙어야 할 곳은 이제 이 서버 밖이다.
