같은 모델과 프롬프트라도 노트북에서 한 번 부를 때와 여러 사용자가 기다릴 때는 다르게 움직인다. 요청이 줄을 서고, 연결이 끊기고, 문서와 프롬프트의 버전이 바뀐다. 운영은 모델을 서버 프로세스에 넣는 일로 끝나지 않는다. 요청을 받아도 되는지 판단하고, 실패 위치를 찾고, 이전 상태로 돌아갈 수 있어야 한다. 실제 로컬 모델과 파일 DB를 쓰는 작은 HTTP 서버는 기능 연결의 증거고, 부하·마감·롤백을 보여 주는 비동기 실험은 통제 장치의 증거다. 둘을 섞지 않는다.

## 요청 경로와 배포 단위

<ServeRequestPath />

```bash
books/ai-engineering/examples/.venv/bin/python books/ai-engineering/examples/book_service.py --state /tmp/hanul-book init
export BOOK_LOCAL_TOKEN="$(python3 -c 'import secrets; print(secrets.token_urlsafe(32))')"
books/ai-engineering/examples/.venv/bin/python books/ai-engineering/examples/book_service.py --state /tmp/hanul-book serve --port 8765 --prompt-version rag-local-v2
```

`book_service.py`는 SQLite 저장소, `respond`, 로컬 E5와 Qwen을 연결한다. `init`은 가상 교육비 개정 문서와 `hanul/reader`의 권한을 준비하고, 재실행은 문서 저장소의 순번 규칙을 따른다. 시작할 때마다 권한을 자동 부여하라는 예제와는 다르다. 토큰은 현재 터미널의 환경에만 두고 원고·커밋·로그에 붙이지 않는다. `ready`가 찍히면 모델 로드와 포트 바인딩이 끝났다는 뜻이고 답변 품질과는 무관하다. Python 공식 문서도 `http.server`를 운영용으로 권하지 않는다. [Python HTTP 서버 문서](https://docs.python.org/3/library/http.server.html)

```python
import json, os, urllib.request
request = urllib.request.Request(
    "http://127.0.0.1:8765/ask",
    data=json.dumps({"question": "교육비 한도와 신청 순서는?"}).encode(),
    headers={"Content-Type": "application/json",
             "Authorization": "Bearer " + os.environ["BOOK_LOCAL_TOKEN"]},
)
with urllib.request.urlopen(request, timeout=60) as response:
    result = json.load(response)
```

클라이언트가 받은 HTTP 200 안에도 `contract_failed`가 있을 수 있다. 요청 처리와 업무 결과를 나눠 응답 본문에 업무 상태를 싣는다. 제품 API라면 상태별 HTTP 매핑을 명세로 정해 모든 클라이언트가 같은 뜻으로 읽게 한다.

## 추적 ID와 관측 신호

추적 ID는 한 요청의 경로를 잇는 식별자다. 여러 프로세스가 참여하면 전체 요청의 추적 아래 검색·모델 호출·도구 실행을 구간으로 나눈다. OpenTelemetry는 이 구간을 span이라 부르고 부모·자식 관계와 속성·이벤트를 붙인다. 최소 서버는 요청마다 새 ID를 만들고 상태, 프롬프트 버전, 전체 처리 시간을 JSON 로그로 남긴다. 질문·문서·토큰은 기본 로그에 없다. 다른 시스템과 이을 때 신뢰하지 않는 추적 헤더를 업무 권한으로 쓰지 않는다. [OpenTelemetry 추적 개념](https://opentelemetry.io/docs/concepts/signals/traces/)

| 신호 | 항목 |
|---|---|
| 기본 네 축 (Google SRE) | 지연 · 요청량 · 오류 · 자원 포화 |
| AI 품질 신호 | 생성 완료율 · 형식 실패 · 근거 부족 · 인용 실패 · 확인 대기 |
| 근거 부족이 늘었을 때 함께 볼 것 | 검색 후보 수 · 색인 버전 · 권한 변경 · 생성 호출 유무 |
| 라벨로 쓰지 않을 것 | 오류 문자열 전문 · 사용자 ID · 질문 |

근거 부족이 늘었다고 바로 장애가 아니다. 답할 수 없는 질문이 늘었을 수도, 권한·색인·문맥 구성이 깨졌을 수도 있다. 상태 코드는 제한된 집합으로 두고 요청별 세부는 접근 통제된 로그나 추적으로 연결한다. [Google SRE 모니터링](https://sre.google/sre-book/monitoring-distributed-systems/)

## 큐 · 역압 · 마감

<QueueDeadline />

```python
try:
    async with asyncio.timeout_at(deadline):
        await simulated_dependency()
except TimeoutError:
    status = "deadline_exceeded"
```

요청을 동시에 돌리면 처리량이 늘 수도 있지만 모델 메모리와 CPU·GPU를 경합하고, 같은 모델을 워커마다 복제하면 가중치 메모리도 는다. 대기열은 순간 유입을 흡수하지만 무제한이면 대기 시간과 메모리를 쌓는다. `operations_demo.py`의 16개 거부는 이 실험의 스케줄링과 부하 모양이 만든 결과라 지속 유입 환경의 용량과는 다르다. `asyncio.timeout_at`의 취소는 협력적인 비동기 작업에서 작동한다. 동기 CPU 추론이나 이미 시작한 외부 쓰기는 되돌리지 못한다. `to_thread`로 옮긴 작업도 태스크 취소만으로는 스레드 연산이 멈추지 않는다. 실제 모델 서비스에는 추론 엔진의 취소 기능, 워커 격리, 종료·정산 절차가 필요하다. 현재 HTTP 예제는 요청을 순서대로 처리하며 본문 길이 상한과 소켓 타임아웃만 두고, 추론의 강제 마감과 비동기 큐는 통합하지 않았다. [Python 비동기 큐](https://docs.python.org/3/library/asyncio-queue.html), [Python 태스크와 취소](https://docs.python.org/3/library/asyncio-task.html)

## 지연 분포와 캐시

평균 응답 시간이 같아도 일부 사용자는 훨씬 오래 기다린다. p50·p95 같은 분위수와 시간 초과 비율을 함께 적고, 거부한 요청과 성공한 요청의 분포를 나눈다. 빠르게 거부한 요청을 섞으면 지연이 좋아 보인다. 부하 실험의 p95는 받아들인 네 요청에서 계산했는데 표본 넷에서는 가장 느린 요청에 가까운 값이라 안정된 추정치와 다르다. 실제 부하 실험에는 워밍업, 동시성, 도착률, 입력·출력 길이 분포, 실행 시간, 실패와 재시도가 들어간다. 토큰 사용량이 없으면 비용은 미확인으로 둔다. 로컬 모델도 장치 사용 시간, 유휴 상태, 저장 공간, 운영·검토 비용이 든다.

응답 캐시 키에는 질문만이 아니라 조직·권한 범위, 문서 개정, 프롬프트·모델·스키마, 기준일이 들어가야 한다. 권한 회수 뒤 캐시된 답을 그대로 주면 검색 권한 검사를 우회한다. 정확히 같은 입력의 캐시와 뜻이 비슷한 질문의 캐시는 다르다. 의미 캐시는 “출장비”와 “해외 출장 숙박비”처럼 비슷하지만 정답 조건이 다른 질문을 합칠 수 있다. 이 프로젝트는 최종 답변 캐시를 두지 않았고, 도입한다면 정확 일치 기준선과 무효화 테스트를 먼저 만든다.

## 버전 묶음과 롤백

<ReleaseBundle />

`release-a` 같은 이름만 있고 실제 구성이 없으면 재현할 수 없다. 코드·모델의 버전 복귀와 업무 데이터의 최신성은 따로 판단한다. `service_smoke.py`는 임시 상태 디렉터리를 초기화하고 실제 E5·Qwen을 올린 HTTP 서버로 v2 요청을 확인한 뒤 서버를 내리고 같은 데이터로 v1을 올려 전환을 확인한다.

## 장애 주입과 복구

```bash
books/ai-engineering/examples/.venv/bin/python books/ai-engineering/examples/operations_demo.py
```

<FaultRuns />

실제 복구 절차에는 감지, 영향 범위 확인, 신규 요청 제한, 실행 중 작업 처리, 이전 버전 전환, 정상·실패 사례 재확인이 들어간다. 등록 결과를 알 수 없는 티켓 요청은 같은 멱등성 키로 상태를 조회하거나 재시도한다. 새 키로 다시 등록해 복구하면 중복 업무가 생긴다. 프로세스를 내릴 때도 접수 중단과 실행 중 요청 처리를 나눈다. 읽기 요청은 취소하면 되지만 이미 외부 시스템에 넘긴 변경은 결과 확인이 필요하다. 로컬 티켓은 같은 파일 DB에 있어서 CLI 프로세스가 바뀌어도 같은 초안의 재실행을 확인할 수 있다.

## 관측 도구와 범위

관측 도구는 추적 조회, 지표 집계, 경보, 평가 결과 연결, 운영 편의성으로 비교한다. 전송할 데이터의 범위·저장 위치·보관 기간·권한·내보내기도 함께 본다. 화면이 보기 좋다는 이유로 원문 질문과 문서 전체를 기본 전송하지 않는다. 이 실습이 확인한 범위는 로컬 HTTP 기능 연결, 허용 필드 로그, 파일 DB의 티켓 재실행, 합성 부하의 역압·마감·복귀다. 인터넷 배포, 다중 사용자 인증, 실제 모델의 동시 부하, 외부 티켓 시스템의 복구는 그 밖이다. 서버가 돌아간다는 사실이 모델 품질의 채택 보류를 풀어 주지도 않는다.
